01 — Approach

A scanner that flags everything has told you nothing.

Most of what security tooling produces is technically true and practically useless. A dependency scanner reports every package with a published advisory, whether or not your code ever calls the vulnerable function. A vulnerability platform reports every flaw on every host, whether or not one patch closes forty of them at once. The output is accurate and the volume makes it unactionable.

The work I find interesting is the reduction — the analysis that turns a list into a decision. That means asking whether vulnerable code is reachable before raising an alarm, and knowing that Windows updates are cumulative so hundreds of findings collapse into a handful of actual patches.

It also means being honest about uncertainty. When an analysis cannot prove something is safe, the answer is unproven, not safe. A tool that guesses optimistically to keep its false-positive count down is worse than no tool at all, because the one it guesses wrong on is the one that mattered.

02 — Selected work

sparta-mapper

Open source · Python · In development

Maps CVEs and vendor security advisories to the Aerospace Corporation's SPARTA space-cyber threat framework, automatically.

SPARTA is the space sector's equivalent of MITRE ATT&CK — a shared taxonomy for spacecraft attack techniques, published as a STIX 2.1 bundle. What did not exist was the layer CISA built for ATT&CK with its Decider tool: something that takes a real advisory and tells you which technique it actually is, with reasoning and relevant countermeasures. This is that layer.

Embedding search narrows the full technique set to a handful of candidates, then a model classifies against those with structured reasoning. Retrieval first, because a model chooses better between five plausible options than it ranks a hundred.

Reachability-aware dependency scanning

Design & build

Conventional dependency scanners answer does this package have a published advisory? The more useful question is does our code ever call the vulnerable function? I built a scanner that asks the second one.

Run against a production frontend codebase of roughly 1,500 dependencies, it flagged a few dozen packages carrying known flaws. Reachability analysis cleared the large majority as never invoked by application code. Everything that survived resolved to a single minor-version upgrade.

The design decision I am most pleased with is what happens when reachability cannot be proven either way. The tool returns unproven, never safe. Some findings came back that way. Because they shared a fix with the findings that were confirmed, the caution cost nothing — it was one version bump either way.

Vulnerability-to-patch automation

Design & build

A patch cycle began as a filtered export of high and critical severity flaws directly affecting business operations — over a hundred of them — each needing to be cross-checked by hand against what was already deployed. Estimated at eight to ten minutes apiece, that is more than two working days before any patching starts.

I automated the cross-reference. Two days of triage became about twelve seconds.

The finding that made it worth doing: because Windows updates are cumulative, the newest one already contains every earlier fix. Just under half the reported flaws needed no action at all — they were already closed by updates that had shipped. Applying the same fact per machine collapsed the remaining work by 78%, turning hundreds of individual rows into a few dozen actual patch tickets.

  • Python
  • Data reconciliation
  • Patch management
  • Reporting automation

Endpoint image management

Process design

Building and maintaining a standard endpoint image required nine separate tools with no documented order of operations, which meant the process lived in whoever had done it last. I documented the sequence end to end and rebuilt it as a process another analyst could follow without supervision.
